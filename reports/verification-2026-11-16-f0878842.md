## Findings and integration requests

### A. Landing-page flag count was wrong — independently confirmed; PR #103 has a proposed fix

The live homepage said **0 Flags open** while the linked [Flagged for Review page](https://kanlerxz87-cyber.github.io/Zone1/flagged.html) showed **61 Open items**. On the reviewed main snapshot, `build.py::_flag_count()` searched for `<tr><td class="num"><strong>F...`, but `page_flagged()` emits rows beginning `<tr id="f1"><td...`; the old pattern therefore matched zero rows. The home metric was false, and the same selector meant a duplicate-ID guard could pass without inspecting any flag rows.

**Coordination:** this defect is already being addressed in [PR #103](https://github.com/kanlerxz87-cyber/Zone1/pull/103), which adds a matching count and build guards. Its reported `verify` and annex checks passed, but it was still open at this report's snapshot. Do not duplicate its code changes. After merge/deploy, re-read the live count and confirm it says 61 (or the new current count), not 0.

### B. Requirements page has stale hard-coded counts

At `main` snapshot `4225b95`, the live [Suggestions page](https://kanlerxz87-cyber.github.io/Zone1/suggestions.html) reports 22 suggestions (`SG-01…SG-22`), but requirement A-02 in `data/requirements.json` and [requirements.html](https://kanlerxz87-cyber.github.io/Zone1/requirements.html) says 21 (`SG-01…SG-21`). The live [Questions page](https://kanlerxz87-cyber.github.io/Zone1/questions.html) reports 21 questions, but A-04 says “Twenty questions” and links to “20 questions.”

This is a repository-to-page consistency defect, not an external product fact. The `data/requirements.json` row count note says counts are computed at build time, but these two embedded text/evidence labels are static. **Integration request:** derive the displayed counts from `data/suggestions.json` and `data/questions.json` or update both the row text and evidence labels whenever those registers change. Re-check after the in-flight decision/content PRs settle because they add register rows.

### C. The separately generated `s2/` annex is stale in the committed tree

Read-only command `python3 scripts/build_s2_site.py --check` exited **1** on the reviewed main snapshot and printed:

`index.html`, `pages/executive-summary.html`, `pages/products.html`, `pages/compliance.html`, `pages/economics.html`, `pages/niche.html`, `pages/content-engine.html`, `pages/campaign.html`, `pages/automation.html`, `pages/requirements.html`, `pages/verification.html`, `pages/sources.html`, and `pages/flagged.html`.

The script says `--check` compares committed HTML with an in-memory rebuild. I did not run the write-mode builder or edit `s2/` because this pass owns no `s2/` files. `scripts/ci-check.sh` runs a rebuild **before** `--check`, so that CI sequence can pass after regenerating its working tree; the main Pages workflow does not run `scripts/build_s2_site.py`. This report does not assert what a direct live request to `/s2/` currently returns. **Coordination request:** the owner of the `s2/` annex should compare/rebuild its outputs and ensure a check verifies the committed artifacts, not only a just-regenerated worktree.

### D. Associate-status config and affirmative disclosure need reconciliation

`data/site.json` records `associates_status: "pending"`; the live site says account approval is not confirmed, but its header/footer and structured data still publish the affirmative sentence “As an Amazon Associate I earn from qualifying purchases” and call the publisher an “Independent Amazon Associates publisher.” The public Operating Agreement §5 both requires the Associate statement and warns against misrepresenting the relationship. The account's actual status cannot be established from public sources, and the site itself raises it as Q-03.

This is a **potential inconsistency, not a verified policy violation**. I did not change the disclosure: no account-side fact is available to justify either “approved” or “not approved.” **Owner/integration decision:** confirm status inside Associates Central, or make the pending-state copy conditional so the public site does not assert an unverified relationship. Keep FTC placement requirements in view if affiliate links are active.
