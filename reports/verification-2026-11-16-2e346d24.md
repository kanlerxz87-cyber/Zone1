## E. Defects this pass found in the site itself

Both are reproducible from `git show 9c6deab` (the state this branch was cut from).

| # | Defect | Evidence at `9c6deab` | Fixed by |
|---|---|---|---|
| D1 | The landing page published **"0 Flags open"** beside a 61-row flag register. `_flag_count()` matched `<tr><td class="num">`, but `page_flagged()` has emitted `<tr id="fNN">` since per-row anchors landed in pass 10, so the regex matched nothing. `check_flag_ids_unique()` used the same stale pattern and had therefore been passing **vacuously** on zero rows. | `grep -o '<div class="tile"><b>[0-9]*</b><span>Flags open' index.html` → `<b>0</b>`; `grep -cE '<tr id="f[0-9]+"' flagged.html` → `61`; `python3 -c "import build; print(build._flag_count())"` → `0` | `_flag_count()` corrected; `check_flag_ids_unique()` corrected; new guard `check_flag_count_matches_page()` |
| D2 | `topics.html` had **8 dead in-page links** (`#tp-01, -02, -03, -05, -06, -12, -13, -14`). `page_topics()` emitted the `id="tp-NN"` detail block only when `status != "published"`, but the plan table links every row. Neither `build.py` nor `verify.py` checked fragments — only file targets. | a fragment sweep across all 38 root-build pages returned exactly these 8, all on `topics.html` | every topic now gets a card (published ones link the article); new guard `check_internal_fragments()`; new fragment check in `verify.py` |

**Both new guards were proved to fire, not merely to exist.** Re-introducing the stale
regex made `build.py` exit 1 with *"landing-page flag count (0) disagrees with the
rendered register (61 rows)"*. Removing one topic anchor made it exit 1 with
*"topics.html: href=\"#tp-01\" has no target in topics.html"*. Renaming one id in the
rendered `topics.html` made `verify.py` report
*"FAIL topics.html: dead in-page link -> #tp-01"*. Each was then restored and the build
returned exit 0.
