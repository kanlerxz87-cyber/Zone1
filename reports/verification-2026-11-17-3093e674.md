## 1. The finding this pass exists for

Sixteen passes published a shop whose product links could not earn, and every one of them recorded the
reason as an owner absence. `data/questions.json` Q-04 read *"tag pending"*; requirement **E-02** was
`blocked`; and the money CTAs on all three product pages were the raw `https://link.amazon/<token>` short
links the owner had supplied, unmodified.

The owner's brief of 2026-11-17 removed the absence in four words:

> Selected Tracking ID:shopnow047c-20

That is when the real shape of the defect appeared. `build.py` — the generator that writes every page in
this site — **never opened `data/config.json`**. There was no code path in which a supplied tracking ID
could reach a link, so "we have no tag" and "we have a tag and cannot use it" produced byte-identical
output. The site was not unmonetisable because the owner was slow. It was unmonetisable because the
wiring did not exist, and no gate could see the difference.

A verification register that describes a repository has to be re-tested when the repository changes, or
it becomes a description of an older build. That is the same defect class this project has now caught
five times (typed counts in `data/requirements.json`, the orphan article F74, the 404 page's relative
links F75, the duplicate flag ids, the premise that a `/dp/` Product-information block was unreachable).

## 3. What was built, and what now fails the build

`build.py` 488,658 → 538,368 bytes across eight patch files kept in `session-3093e674/`.

* **One link builder.** `amazon_out_link()` composes `https://www.amazon.com/dp/<ASIN>?tag=<id>` from
  `data/config.json`; `product_cta()` and `cta_inline()` are the two rendered forms, used by the product
  pages, the comparison matrix's new action row, the category table and the picks cards — **12 published
  CTAs**. `data-z1k="outlink"` marks them; the supplied short link stays visible underneath as the
  artefact being checked, not as the destination.
* **`check_special_links()`** asserts on the rendered HTML: a CTA must be a canonical `/dp/<ASIN>` carrying
  the configured tag or an assigned sub-tag; it must not be the redirector; no tag may appear while the
  config declares none; every tag and sub-tag must match `XXXXX-##`; and — added after the proof run below
  — **an untagged money link is now a decision on the record**, not a default: with no tag configured and
  no `affiliate_tag_optout`, any published CTA fails the build by count.
* **`data/link-intent.json` → `links.html`.** Five rows (LI-01…LI-05) keeping *intended* (owner statement
  only) beside *observed* (fetch only) with an `observed_on` date per row. `check_link_intent()` fails if a
  row records the two as the same product unless its status begins *"confirmed by the account holder"*, and
  if any marketed product lacks a covering row.
* **`data/measurement.json` + the ledger in `assets/app.js` → `measurement.html`.** Five events, counted in
  the visitor's own browser, exported or erased on the page, no cookie, no request.
  `check_measurement_contract()` greps the shipped JS for `fetch(`, `XMLHttpRequest`, `sendBeacon`,
  `document.cookie =`, `import(` and `@import`; it fails if a specified event is missing, and it fails
  in the other direction too — an endpoint in the config while any page still says "runs no analytics".
* **`data/campaign-ledger.json`.** The only home for a performance number: a row needs a period, a source
  whose host this repository already recognises, and a date obtained; `revenue`, `forecast`,
  `conversion_rate` and `expected_earnings` are not permitted fields. It ships with **zero rows**, because
  zero observed campaigns is the true count, and `check_campaign_ledger()` will not let anyone improve on
  that by typing.
* **`check_seasonal_expiry()`.** Both seasonal articles carry a validity window in `data/articles.json`,
  the window is printed on the page, and the build stops the day after it closes — the dated form of the
  §2(b) removal duty. The gate reads the calendar; the rendered output does not, so the generator stays
  reproducible.
* **The content the brief listed and the site lacked.** *Questions to ask before buying a multi-function
  kitchen appliance* (TP-21, the fourth hypothesis) and a bridge explainer *Can you put a wireless meat
  thermometer in an air fryer?* built on the read in rows 6–8 above; the front page now opens with the
  buyer's four questions before the format guide.
* **Counts computed where they were typed.** `req_counts()` gained `n_link_rows`, `n_ledger_rows` and
  `n_measure_events`; the handover heading ("Five actions, about an hour, eighteen flags") is now derived
  from its own rows.

## 7. What the next pass should not repeat

1. **Do not read "the register says X" as "X is still true."** The tag was recorded as pending for sixteen
   sessions because nobody re-opened the generator to see whether a config value could reach a link.
2. **A new mechanism needs a new failure mode.** Every rule added here ships with a guard, and every
   guard ships with a proof that it fires. Untagged CTAs were only truly fixed when the absence of a tag
   became a build error — that rule was written after the first proof run, not before it.
3. **Never let a short link be a destination.** It is a redirector whose own parameters are invisible to
   this repository, and it hides the tag question rather than answering it.
4. **Never market the register.** Two candidates are published because they were supplied and read; they
   stay candidates until the owner settles Q-27 and the SKU settles Q-29.
5. `session-3093e674/*.py` are the working scripts of this pass (registers, patches, the guard-proof
   harness). They are committed as evidence, not as part of the site, and `build.py` is the only
   generator.
