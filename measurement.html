Owner workspace · measurement

Measure only what the system can verify.

Five event definitions and a reporting cadence are ready for review. Collection is deliberately disabled: the current GitHub Pages publication has no server endpoint, no verified account connection and no approved analytics privacy notice.

Prepared, not live. The source-controlled collector is a deployment reference, not a live service. This publication currently sends no analytics events. No click totals, conversions, traffic sources or revenue are claimed.

Event definitions

In the reference design, browser payloads contain only allow-listed page/product IDs or a fixed engagement bucket, and the application stores daily aggregates rather than raw event rows. The client reads no cookies, persistent IDs, referrers, query strings or destination URLs. The collector disables its own HTTP access log; host and proxy logging must also be reviewed before deployment. affiliate_report_import is an operator-only aggregate from an authorized report, not a browser event.

What actually ships in this repository

Two event registers exist and both are published: data/analytics-plan.json (the table above — what the reference collector accepts) and data/measurement.json (the cards below — what the shipped browser counter sends). They are parallel descriptions of the same five events written by different sessions; nothing is collected by either until every gate above passes. The client-side IDs map one-to-one: EV-01 page_view, EV-02 outbound_product_click (the plan's outbound_click), EV-03 guide_completed (article_engagement), EV-04 comparison_table_viewed (comparison_interaction), EV-05 reported_order (affiliate_report_import, operator-entered).

The client-side events, in detail

EV-01 · page_view

Fires when: A human opens any article, product, comparison or guide page. The page type is derived from the URL by the build, so a new page is classified by where it lives.

Records

  • page slug
  • UTC date
  • whether the arrival carried a utm_source/campaign parameter

Never records

  • IP address
  • user agent
  • referrer URL
  • reader identifier

Slug and date only. A per-reader identifier would turn this into behavioural tracking and break the no-cookie statement. The utm parameter is recorded as a yes/no, not as its value: the value is what would let one page tell which channel sent it, and that is a wider question for the owner, not a detail this pass may settle (Q-29).

EV-02 · outbound_product_click

Fires when: A reader clicks any link whose href points at www.amazon.com/dp/<ASIN>.

Records

  • ASIN
  • page slug the click came from
  • UTC date
  • the Associates tag present on the link

Never records

  • order value
  • what the reader bought
  • any Amazon session data

This is the earliest point at which this site can observe intent without Amazon's data. It counts interest, not revenue, and must never be labelled a conversion. The ASIN is read from the link the reader actually clicked, so it is the destination they were sent to, not the one the site would have preferred.

EV-03 · guide_completed

Fires when: A reader scrolls a sourced article to its final section, measured at the last heading, not at the footer.

Records

  • page slug
  • UTC date

Never records

  • time on page
  • scroll depth histogram
  • reader identifier

A single completion flag is enough to answer 'did anyone read this'. A depth histogram costs a cookie-free session id and buys nothing the editorial calendar uses. The last heading of every article carries the marker attribute the observer watches.

EV-04 · comparison_table_viewed

Fires when: The comparison table becomes visible in the viewport on compare.html or on the landing page's side-by-side table.

Records

  • page slug
  • UTC date

Never records

  • which rows were expanded
  • reader identifier

Exists to test one editorial hypothesis: whether the comparison surface is the thing that earns clicks, or whether the articles do.

EV-05 · reported_order

Fires when: Never automatically. It is entered by hand from an Amazon Associates Central order report for a dated period.

Records

  • report period start/end
  • ASIN (when the report itemises one)
  • reported clicking-site subtag
  • orders
  • reported revenue
  • date the report was read

Never records

  • inferred or modelled orders
  • a conversion rate computed from mismatched windows

This is the only revenue-bearing event, and it is first-party: it comes from the owner's authorised report, never from this site. A score or forecast is deliberately absent.

Privacy rules the counter must keep
  • No cookies are set by the counter. If a cookie is ever added, the footer statement and the §3(e) disclosure change in the same commit — and the build guard fails if the counter file grows a cookie or storage call.
  • No persistent identifier per reader and no cross-site profile. Program Policies §2(b) separately forbids associating a sub-tag with a specific end user.
  • The counter records the event, the page slug, the product ASIN, the date and the tracking ID present on the link — never an IP address, user agent string or referrer. The client never reads those three values at all, which is checked by the build guard rather than promised in prose.
  • Program Policies §3(s) forbids artificially generating clicks; the counter fires only inside a click listener that requires event.isTrusted and a primary button, on a link whose href contains /dp/<ASIN>. Nothing fires on load, on scroll alone, or from a synthetic dispatchEvent, and the handler never calls preventDefault, so the reader's click always reaches Amazon.
  • The request itself necessarily exposes the reader's IP address to the server that receives it. That is a property of HTTP, not something the client can prevent. The shipped endpoints drop the address without writing it to disk; the host's own web-server access log is outside this site's control and is stated here rather than glossed over.

Why nothing is sending yet

  • The site is static files on GitHub Pages. There is no server to receive a beacon, so the 'self-hosted analytics endpoint' has to live on a host the account holder controls. The endpoint source now ships in analytics/ (a PHP file and a Cloudflare Worker), but this repository cannot deploy it and does not pretend to have.
  • A click counter that reported a number without a real endpoint behind it would be an invented number on a page that promises every value is sourced. The counter therefore ships with the switch off, and no count appears anywhere on this site.
  • The footer's cookie and third-party-technology statement is now GENERATED from the same configuration block that decides whether the counter ships, so it cannot describe a behaviour the page does not have. Program Policies §3(e) is satisfied by construction rather than by a sentence somebody has to remember to update.
  • Amazon's own conversion reporting lives in Associates Central and is not available to a third-party static site, so reported orders must come from the owner's first-party report, not from this site.

Cookies & privacy

This site sets no cookies itself, runs no analytics, and has no comment forms or accounts. This GitHub Pages build sends no analytics events: the proposed first-party collector is not deployed and browser collection remains disabled. Following an Amazon link takes you to Amazon, whose own privacy notice and cookie practices apply from that point. No data you enter here is collected, because there is nowhere to enter it.

Amazon's Program Policies §3(e) require an accurate statement of cookie and third-party technology use on Associate sites. This notice satisfies that requirement for the current build; it must be updated the moment any analytics, embeds or affiliate-network script is added. The outbound-click counter for this site is written and shipped in assets/analytics.js but is switched off, because no endpoint host has been chosen — so nothing is sent from your browser to anyone. The paragraph above is generated from that switch, so it cannot describe a behaviour the page does not have.
