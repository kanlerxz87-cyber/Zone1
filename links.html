Where the links you sent actually go

Five Amazon links were supplied to this project, and every buying decision on this site rests on knowing which product each one points at. This page keeps two answers side by side and deliberately apart: what the account holder intended, and where a fetch landed. A reader following a link gets the second; only the first can justify a recommendation, and it has not been given to us yet.

Why the two columns are never merged. An observed redirect is a machine-readable fact: a fetch either landed on amazon.com/dp/B0CDY277D3 or it did not. An intended ASIN is a fact about a person's decision, and the only source for it is the account holder. Merging them is how a verification register turns into a story: the site would publish 'the owner meant this product' on the strength of where a redirector happened to land on one afternoon. The three original links were adopted as the site's product set on the strength of their destinations alone, which is why F6, F7 and F10 have stayed open for four days and why this page exists.

Rules this register is held to

  • The 'intended' object is filled only from a statement by the account holder. A fetch never fills it.
  • The 'observed' object is filled only from a live fetch of the submitted URL, with the date and the method. A human statement never fills it.
  • No row may present the two as one value, and no page renders intended_asin from observed_final_asin.
  • A destination that is stable across repeat reads is recorded as 'stable'; it is never recorded as 'confirmed', because stability of a redirector says nothing about intent.
  • If the two disagree, the link is removed from the money pages first and the row is corrected afterwards, not the other way round.

The ASIN check, before anything else

Every submitted token in this register is 9 characters long. An Amazon ASIN is a 10-character identifier and the canonical detail-page URL is amazon.com/dp/ASIN, so none of these tokens is an ASIN: each is a short-link slug that resolves to one.

Reading the token as an ASIN is the single most likely way this project could have published a wrong product. amazon.com/dp/B04G1MEwY returns 404, which is what proves the point rather than asserting it. S23

What changed on 2026-11-17: the links now carry the Associates tag

A link from this site to Amazon is only a Special Link if it carries the Associates ID: 'Special Links must use the Associates ID we have assigned to you', and the tag must appear 'as a parameter in the URL of each link you place on your Site to an Amazon Site'. Amazon also states it has no obligation to pay fees if the links are not properly formatted. S2 S1

build.py composes every product link as https://www.amazon.com/dp/<ASIN>?tag=<tag from data/config.json>, and check_special_links() fails the build if any Amazon-bound product link on a generated page lacks the configured tag while a tag is configured. The supplied short link is still shown, labelled as what it is, because it is the artefact the owner handed over and the only thing that can be checked against their account.

That single test is an owner action (Q-04, handover.html).

How the link was checked, in order

  1. The submitted URL was fetched on 2026-11-17; its own landing link and document title were read. S17
  2. The destination ASIN was compared against the ASIN this site already markets, so a moved redirect would be visible instead of quiet. S16 S28 S29 S36 S37
  3. The tag parameter was looked for on the landing URL. It is not observable from outside an Associates account, which is why that half stays an owner action rather than a green tick. S6
  4. The composed Special Link is published from data/config.json by one function, so no page can carry a product link that forgot the tag — and the build fails if one does.

What this page does not claim

  • This register does not claim the supplied short links are invalid or non-compliant. Their exact compliance status is unresolved and is recorded as F7 and F10.
  • It does not claim that tagging a canonical /dp/ URL produces a paid attribution. That is what the one-link test in handover.html is for.
  • It does not record any click, order or revenue figure. See campaign-ledger.html for the register that is deliberately empty.

If you are the account holder

  1. If the owner confirms an intended ASIN for a row, the site's product mapping changes to match and this row records the confirmation with its date and wording.
  2. If the owner says the intended ASIN differs from the observed one, the affected page's CTA is pulled in the same commit that records the row, per rule 5.
  3. A row never moves to 'confirmed' because a fetch was repeated. Only a statement from the account holder moves it.
