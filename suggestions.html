Suggestions, and a place to choose between them

23 reviewed, evidence-backed suggestions, in priority order. Each one would materially change something on this site. Nothing on this page has been implemented. Each entry names the problem it fixes, the official document or repository evidence behind it, two or three paths you could take, and the path this pass would pick if it were your call. Read the one you care about, choose a path, and the work is a short story rather than an open-ended project.

How to use this page. Nothing on this page has been implemented. It is a decision queue for the site owner. The score is priority = impact (1-5) x confidence that the evidence supports it (1-5). Both are this pass's judgement. The evidence links are the facts; the score is the opinion. Suggestions blocked by something only you can supply link to the exact row on the Open questions page.

Choose a path before you choose a suggestion

A decision queue with this many rows is a backlog, not a decision. The paths below group the suggestions into four coherent pieces of work. Each path is ordered, names what has to be true before it can start, and says plainly what it will not fix. Pick one path, finish it, then pick the next. The grouping is this pass's judgement; the dependencies inside it are not - they are the blocked_by links already recorded on each row.

SG-01 · Product identity

Settle which exact model each supplied link points to, before any more content ships

25priority

The problem. The site markets three products but cannot state which manufacturer model each Amazon listing is. Chefman publishes three 6-quart dual-basket models (RJ38-3DBW-V2, RJ38-SQPF-3TDB-2, RJ38-SQPF-3TDB-2W) and the 8-quart ASIN carries a 450 F Hi-Fry claim that the RJ38-SQSS-8T manual does not support. A buyer who lands on the wrong spec table is the one failure mode that costs both trust and money.

Evidence. Chefman 6 Qt dual-window product page (model RJ38-SQPF-3TDB-2W) ↗ Chefman 6 Qt dual-basket product page (sister SKU) ↗ Chefman 8 Qt product page ↗ Root flag register, rows F2, F3, F32, F33 ↗

Paths you could take

  1. A. Read the model number off each live listing (5 minutes, no code)
    Effort S · risk none · reversible
    Open each of the three Amazon links, scroll to the Product information table, and read the 'Model Number' row. Paste the three strings into a reply. That single act closes F2, F3, F32 and F33 at once.
  2. B. Stop publishing per-model spec tables until A is done
    Effort M · risk medium · reversible
    Demote the three product pages to a comparison of confirmed features only, with the model line blank and flagged. Costs the site its differentiation but removes every wrong-model risk.
  3. C. Ask the manufacturer
    Effort M · risk low · reversible
    Chefman and Emeril Everyday support can confirm which SKU an ASIN maps to. Slower than A and usually less authoritative than the listing itself.

This pass would pick: A, then keep publishing.

Why. Amazon does not publish ASIN-to-model mappings anywhere machine-readable, and the brand sites publish model numbers independently of the listing. The two only meet inside the listing's own Product information block, which is visible to you in a browser and to nobody without one. Every other route is inference, and inference is exactly what this project refuses to publish.

Cost of not doing it. High. A wrong spec table is a factual misstatement about a product you are paid to recommend, and it is the kind of error that attracts both refunds and FTC attention.

SG-07 · Compliance guardrail

Do not build price tracking or price alerts, whatever the brief asks for

25priority

The problem. The brief asks for a platform that 'analyzes pricing' and 'continuously optimizes campaigns'. Program Policies section 6(y) states that, unless otherwise agreed by Amazon, your Site must not have price tracking and/or price alerting functionality. A price-history chart or a 'notify me when it drops' feature is the most natural thing to build next and it is expressly prohibited.

Evidence. Program Policies, section 6(y) ↗ Platform blueprint page, guardrails section ↗

Paths you could take

  1. A. Write the prohibition into the build as a failing test
    Effort S · risk none · reversible
    A CI check that fails if a price-history, price-alert or chart component ever appears in a generated page or a data file. The rule then cannot be broken by accident in a later pass.
  2. B. Document it and rely on reviewers
    Effort none · risk medium · reversible
    A note in the platform page. Costs nothing and fails the first time an enthusiastic session does not read it.
  3. C. Request Amazon's written agreement
    Effort L · risk low · reversible
    Section 6(y) says 'unless otherwise agreed by Amazon', so a written exception is theoretically available. Realistically not granted to a new account.

This pass would pick: A. Make the policy executable.

Why. This repository already proves the technique works: build.py refuses to publish a spec row that has a value but no source. The same mechanism should refuse to publish a price-history feature. A policy that lives only in prose gets broken by the next well-meaning pass.

Cost of not doing it. High. Price tracking is the most commonly requested affiliate feature and the most clearly prohibited one here.

Blocked by: Nothing blocks this.

SG-18 · Platform and compliance

Decide what the AI agent in the brief is allowed to read, before the pipeline is written

25priority

The problem. The brief asks for an AI platform that "automates product research, identifies trending and high-converting products, analyses pricing, reviews, competition, and commission potential". Read against Amazon's IP License, most of the automatic half of that is contractually closed. Section 1 states that Amazon "will not allow any third party to use Program Content to, directly or indirectly, develop or improve large language or multimodal models, machine learning models or related technology". Section 2(e) forbids accessing Creators API, PA API or Data Feeds "for the purpose of aggregating, analyzing, extracting, or repurposing any Product Advertising Content ... or in the direct training or fine-tuning of a machine learning and/or foundational model" without Amazon's express prior written approval. An Amazon listing's title, price, rating and review count are Program Content. An agent that reads Amazon listings to learn what sells is therefore the exact use the licence names; an agent that reads manufacturers' own product pages and owner's manuals is not. This is a constraint on design, and it is cheapest to honour before the pipeline is written.

Evidence. Associates Program IP License, section 1 - Program Content and large language models ↗ Associates Program IP License, section 2(e) - aggregating, analysing, repurposing, and model training ↗

Paths you could take

  1. A. Build the platform on manufacturer and first-party data only
    Effort L · risk low · reversible
    Research the manufacturers' own product pages and owner's manuals, keep the verified dataset as the single source of truth, and let the generator write only what that dataset contains. This repository already implements the pattern: build.py refuses to publish an article whose numbers are not in data/products.json, and every value on the site carries the official page it came from. Trend and niche signals then come from your own click and earnings data rather than from Amazon's listings.
  2. B. Apply for Creators API or PA API and operate inside the API licence
    Effort L · risk medium
    The APIs are the sanctioned route to Amazon data, and their output may be displayed under sections 2(b) and 6(t) with the required display rules. Credentials are tied to the primary account holder and request volume scales with account sales, so this path depends on Q-05 and Q-03 being answered first.
  3. C. Ask Amazon for prior written approval to use listing content
    Effort M · risk low · reversible
    Section 2(e) allows the use with Amazon's express prior written approval. Until that approval exists in writing, any version of option A that reads listing text is the prohibited use.

This pass would pick: A, treating B as the later upgrade rather than the starting point.

Why. The headline capability in the brief is the part the licence most clearly constrains, and knowing that before the research pipeline is designed costs nothing, while discovering it afterwards costs the pipeline. Option A is not a reduced version of the brief: it is the version of it that is lawful, and this repository already demonstrates that it can be built - the whole site is a working example of manufacturer-sourced, machine-written, claim-checked content.

Cost of not doing it. High. A pipeline built on scraped listing content that later turns out to be the prohibited use means discarding the pipeline, and potentially the account, at the point where the most has been spent.

Blocked by: Nothing blocks this.

SG-02 · Attribution and revenue

Confirm the Associates tag is actually inside the three supplied links

20priority

The problem. The three links are link.amazon short links. The Associates tag (the 'tag=xxxxx-20' parameter) is inside the redirect and cannot be observed from outside. If the tag is missing, wrong, or belongs to a different account, every click on this site earns nothing, and nothing on the site would reveal it.

Evidence. Program Policies, section 2(a): Special Links must use the Associates ID assigned to you ↗ Program Policies, section 2(b): the tag must appear as a parameter in each link to an Amazon Site ↗ Flag F6, root register ↗

Paths you could take

  1. A. Open each link while signed in to Associates Central and watch the click register
    Effort S · risk none · reversible
    Associates Central reports clicks per tag in near-real time. One click on each link, then check Reports > Link Type. Confirms tag presence and ownership together.
  2. B. Replace the short links with full amazon.com URLs carrying your tag explicitly
    Effort S · risk low · reversible
    Rebuild each link as https://www.amazon.com/dp/ASIN?tag=YOURTAG-20 and read the tag back on the page. Makes the tag visible in the HTML, which is auditable and satisfies section 2(b) on its face.
  3. C. Keep the short links and hope
    Effort none · risk high · reversible
    No action. The revenue risk is unquantifiable and unmonitored.

This pass would pick: B, with A as the confirmation step. Replacing the short links also removes the link-shortening question in section 6(w) entirely.

Why. Section 6(w) forbids link shortening 'in a manner that makes it unclear that you are linking to an Amazon Site', and link.amazon keeps the Amazon name so it is probably compliant - but 'probably' is doing the work. A full amazon.com URL with a visible tag is unambiguous on both section 2(b) and 6(w), and it makes the single most commercially important fact on the site verifiable from the page source.

Cost of not doing it. Critical. Every other improvement on this page is worthless if the clicks do not credit your account.

Blocked by: Q-03 Q-04

SG-03 · Trust and compliance

Say who wrote each page and how it was made - and stop calling the site 'independent'

20priority

The problem. The site presents itself as 'an independent affiliate publisher' while monetising every product page. 16 CFR 465.6 makes it deceptive for a business to materially misrepresent that a website it controls provides independent reviews or opinions. Separately, the pages do not say that the analysis is documentation-based and machine-assisted, which a reader will assume is hands-on testing unless told otherwise.

Evidence. 16 CFR 465.6 - company-controlled review websites ↗ 16 CFR 255.5 - disclosure of material connections ↗ FTC Endorsement Guides Q&A ↗

Paths you could take

  1. A. Replace 'independent' with a precise, verifiable claim
    Effort S · risk none · reversible
    'Every specification on this page is quoted from the manufacturer or the US Code of Federal Regulations. We do not do hands-on testing and we say so on every product page.' Same pride, no misrepresentation.
  2. B. Add an About page naming the method and the author
    Effort S · risk none · reversible
    One page: who runs the site, how products are chosen, that AI assists with drafting, how corrections are handled, and how the site earns money. Link it from the footer of every page.
  3. C. Leave the framing and rely on the disclosure bar
    Effort none · risk high · reversible
    The Amazon disclosure sentence stays in the bar. The 'independent' claim and the missing method statement stay too.

This pass would pick: A and B together. This is the cheapest trust gain available on the site.

Why. The current copy is already honest about not testing - it just buries that in the footer instead of carrying it as the site's actual selling point. 'We quote the manual, page and section' is a stronger differentiator than 'independent', which is a word every affiliate site uses and which now carries regulatory weight under 16 CFR 465.6.

Cost of not doing it. Medium-high. The word 'independent' next to affiliate links is the specific fact pattern 465.6 was written for.

Blocked by: Q-09

SG-20 · Catalogue

Decide the product set before the next content push

20priority

The problem. The site covers three air fryers, two of them from the same brand and two of them in the same form factor, so the comparison a reader can make here today is narrow. The category is much wider than that: the Amazon listing pages the site's own links open carry Amazon's own related-listing carousels, and those name the competing French-door ovens and dual-basket fryers a shopper in this niche is actually choosing between - each with a manufacturer's product page and manual that this project already knows how to verify to the standard the site holds. Adding the direct competitors is the largest single lever on both organic traffic and commission, and also the largest block of new verification work.

Evidence. Amazon listing for B09B7SB46R - related-listing carousel naming competing French-door ovens ↗ Amazon listing for B0CDY277D3 - related-listing carousel naming competing dual-basket fryers ↗

Paths you could take

    Effort L · risk low · reversible

  2. B. Keep three products and widen by format instead
    Effort M · risk low · reversible
    Add one product per form factor the site already explains, so the comparison is about air fryer types rather than about these three particular units.
  3. C. Stay at three products
    Effort none · risk medium
    The narrowest option and the cheapest to keep verified. It caps traffic at whatever a few exact-match queries can bring.

Why. Organic traffic in this niche is won by covering the comparison a buyer is making, not by covering one product deeply. Cost of not doing it. High. Every week spent deepening three pages is a week not spent on the pages a comparison search lands on.

SG-06 · Catalogue data

Publish no Amazon price or rating unless you hold Creators API access - and know which one you are choosing

16priority

The problem. The site displays no Amazon price, availability, star rating or review count. That is deliberately correct: Program Policies section 2(b) permits price and availability only when Amazon serves the link or when the data comes from Creators API or PA API, and section 6(t) restricts customer reviews and star ratings to API-served content. But it leaves a comparison table with a 'not displayed' column, which is a weaker buying aid than readers expect.

Evidence. Program Policies, section 2(b) (price and availability) and 6(t) (reviews and star ratings) ↗ Creators API / PA-API 5 deprecation notice ↗ Article explaining the policy to readers ↗

Paths you could take

  1. A. Ship compliant price via the Amazon-served link, and nothing else
    Effort M · risk low · reversible
    Use Amazon's own link widgets, which are served by Amazon and therefore permitted under 2(b). No API keys needed. The price is rendered by Amazon, not scraped by you.
  2. B. Apply for Creators API and render price and rating from it

SG-22 · Platform compliance

Decide what the research agent is, and declare it in every request

16priority

The problem. The brief asks for an AI-powered platform that automates product research, and Amazon's Program Policies contain a section written for exactly that case: IP License §4, the Agent Terms. Read live on 2026-11-16, they require any agent that touches Program Content to identify itself in every HTTP/HTTPS request as "Agent/[agent name]", to avoid obfuscating that it is an agent, never to complete or circumvent a CAPTCHA, and to answer truthfully when asked whether an interaction is human. Amazon also reserves the right to limit agent access by technical measures. None of this was in the canonical compliance register or the platform blueprint before 2026-11-16, even though the site ships an automation blueprint that proposes automated research against manufacturer and Amazon pages. Two things are still unresolved: whether an ordinary public listing page counts as Program Content (the licence defines Program Content around Creators API, PA API and Data Feeds), and the agent's declared name.

Evidence. Associates Program IP License §4 (Agents) - read live 2026-11-16 ↗ Associates Program Participation Requirements §5 - no Special Links or Program Content used to develop machine-learning models without express prior written approval ↗ Associates Program IP License §1 - no third party may use Program Content to develop or improve large language or multimodal models ↗

Paths you could take

  1. A. Identify as an agent, and keep the research stage off Program Content
    Effort S · risk low · reversible
    Give the fetcher a fixed User-Agent of the form "Agent/zone1-research", never solve or evade a bot check, and scope the research stage to manufacturer pages and other non-Program-Content sources. This satisfies the Agent Terms whether or not a listing page turns out to be Program Content, and it is the design the site's own compliance posture already implies: it publishes no Program Content today.
  2. B. Ask Amazon first, then build
    Effort S · risk low · reversible
    Send one written question to Associates Central support: does an automated fetch of a public amazon.com product page count as accessing Program Content under IP License §4, and is a given Agent/... User-Agent acceptable? Build nothing until the answer arrives. The safest order, and the one that costs the most calendar time.
  3. C. Leave the research stage manual
    Effort none · risk low · reversible
    Keep automated fetching for manufacturer pages and the Amazon Associates help pages only - the sources this site actually reads - and do not automate anything against amazon.com listing pages. The Agent Terms then never bind, because no agent touches Program Content.

This pass would pick: A, with B running alongside it, and C as the fallback if Amazon says no. The two questions in Q-21 - what counts as Program Content, and what the agent is called - are both cheap to ask and cheap to answer wrongly, so ask while the design is still cheap.

Why. This is the one place where the platform the brief describes meets a rule written for platforms exactly like it. Handling it deliberately costs a User-Agent string and a written question. Handling it by accident, after a research agent has been running for months against Amazon pages, costs the licence. The published site is unaffected either way, which is why this sits in the queue rather than on the compliance page as a live breach.

Cost of not doing it. High, and rising. The site currently makes no automated request against an Amazon listing page in its build; the moment a research agent is switched on, the Agent Terms apply, and an agent that does not identify itself is outside the licence. The cost of doing this later is a rewrite of the fetcher rather than a header change.
